# Mission Control v2 Audit - 2026-10-09

## Verdict

Mission Control v2 is online and receiving live runtime data. It was not fully broken, but it had two operational issues that could make it look offline or outdated:

- The real LaunchAgent was `ai.gustav.workspace-server`, but this was not documented in the repo.
- Runtime logs had grown very large, especially `runtime-events.ndjson`, making restart/replay unnecessarily heavy.

## Verified Live State

- Local URL: `http://127.0.0.1:18792/v2.html`
- Service: `ai.gustav.workspace-server`
- Runtime bridge: connected to `ws://127.0.0.1:18789`
- Tracked sessions: 52
- Subscribed sessions: 52
- Backfill failures: 0
- Snapshot API: live and returning Gustav from runtime state

## Stale Areas

The runtime plane is live, but several file-backed executive sources are stale:

- `executive/goals.json`
- `executive/club-snapshot.json`
- `executive/projects.json`
- `todo.json`
- `roi.json`
- `sirius-status.json`

This means the hub currently works best as a live operations console, but its strategic/executive overview is not yet a trustworthy current business dashboard.

## Fixes Applied

- Added tail-based NDJSON loading so startup no longer reads full multi-hundred-MB or GB logs.
- Added startup compaction for oversized runtime/transcript logs.
- Updated the existing `ai.gustav.workspace-server` LaunchAgent with explicit Mission Control environment variables and durable log paths.
- Removed the duplicate temporary Mission Control LaunchAgent from active use.
- Restarted and verified a single launchd-managed process.

## Next Work

- Refresh the executive source files from current workspace memory and live project state.
- Add a visible "file plane stale" indicator to V2 so stale strategic panels cannot masquerade as live data.
- Consider replacing file-backed status JSON for Altair/Lyra/Sirius with the same runtime subscription model Gustav uses.
